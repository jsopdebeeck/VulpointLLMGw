LLMGW, la passerelle IA de l'organisation

Un point de connexion unique entre les utilisateurs, les agents et les modèles de langage. Il applique la politique IA : qui peut utiliser quel modèle, quelles données peuvent sortir, et avec quelle traçabilité.

Version 1.5.3 (23 octobre 2026)Composant llmgw (binaire unique Go, macOS et Linux)Formats d'API OpenAI et AnthropicInterface anglais, français, néerlandais
Guide utilisateur du chat ↗
Fonctionnalités

1Objectif

Renforcer la politique IA en imposant un passage unique vers les LLM. Les accès directs aux fournisseurs (OpenAI, Anthropic, Mistral, DeepSeek…) sont bloqués dans les firewalls et dans Cisco Umbrella. Seule la passerelle est autorisée à les joindre.

Ce point central permet de :

  • contrôler l'accès : chaque utilisateur ou application s'identifie avec sa propre clé et reçoit un profil ;
  • protéger les données : les informations sensibles sont remplacées par des jetons avant de quitter l'organisation, puis restaurées dans la réponse ;
  • choisir le modèle selon le profil, avec repli automatique en cas de panne ;
  • mesurer les volumes, les temps de réponse, les conversions et les violations.

2Architecture

À gauche, la zone de confiance : les utilisateurs, les agents, les applications et les LLM locaux. À droite, Internet, zone non maîtrisée : les LLM cloud. La passerelle se place en bordure : toute requête vers un LLM la traverse, et c'est le seul composant autorisé à sortir vers les fournisseurs.

Figure 1. Zone de confiance à gauche, Internet à droite, passerelle en bordure. Flux autorisés en traits pleins ; accès direct vers Internet bloqué (pointillés rouges).

3Accès

Portail web /chat

Pour les utilisateurs. Connexion avec Microsoft (Entra ID), Google ou la clé personnelle, puis choix d'un modèle parmi ceux autorisés par le profil. Sans accès, une personne peut en faire la demande (voir Demandes d'accès).

  • Documents joints : txt, md, csv, json, PDF, docx. Le texte est extrait dans le navigateur, puis anonymisé par la passerelle.
  • Images et fichiers traités selon le profil : transmis, remplacés par un carré blanc ou refusés (voir 11. Images et fichiers).
  • Historique des 10 dernières conversations, conservé dans le navigateur ; bouton Aide vers le guide utilisateur.
  • Sous chaque réponse : le modèle utilisé et le nombre de données pseudonymisées.

API agents et applications

Pour les agents (Claude Cowork, Claude Code, Hermes) et les applications. Même adresse que le portail, avec une clé d'application.

  • Format OpenAI : /v1/chat/completions, /v1/models.
  • Format Anthropic : /v1/messages, /v1/messages/count_tokens.
  • /v1/me : profil, quotas et consommation de l'appelant.
  • Streaming pris en charge dans les deux formats.

4Authentification

Chaque accès est identifié. Trois méthodes coexistent ; le SSO s'ajoute aux clés sans les remplacer.

MéthodePour quiOù
SSO OpenID Connectpersonnes : Microsoft Entra ID, Google, ou tout fournisseur OIDC (Okta, Keycloak…)portail web et dashboard
Clé gatewaypersonnes sans SSO, agents et applicationsportail web (désactivable) et API
Jeton d'administrationadministrateur technique, secoursdashboard

Profil attribué après une connexion SSO

  1. Un utilisateur déclaré avec la même adresse email garde son profil et ses quotas.
  2. Sinon, la première règle qui correspond : groupe Entra → profil, rôle d'application → profil, ou motif d'email (*@exemple.be) → profil.
  3. Sinon, le profil par défaut du fournisseur.
  4. Sinon, l'accès est refusé avec un message explicite.

Les administrateurs sont désignés par rôle d'application, groupe Entra ou adresse email, ou listés dans les comptes d'administration (Admin ou Support) : ils ouvrent le dashboard sans jeton. Google ne transmet pas les groupes : avec Google, les profils s'attribuent par domaine, par email ou par utilisateur déclaré.

Les arrivées, départs et changements de service suivent l'annuaire. Le rôle et le profil sont recalculés à chaque requête avec la configuration en vigueur : retirer une règle, un compte ou un utilisateur s'applique tout de suite. Un changement de groupe dans l'annuaire s'applique à la connexion suivante (session de 12 heures par défaut). La déconnexion révoque la session, même si son cookie a été copié.

Identité retenue : pour Entra ID, l'UPN, fixé par les administrateurs du tenant ; pour Google et les autres fournisseurs OIDC, l'adresse email marquée vérifiée par le fournisseur, sinon la connexion est refusée. Un fournisseur OIDC qui ne transmet pas ce marqueur s'accepte avec trust_unverified_email = true, seulement si personne ne peut s'y inscrire librement.

Demandes d'accès

Une personne sans accès peut le demander depuis l'écran de connexion du chat (lien « Demander un accès » : nom, email, motif). Section [access], onglet Demandes d'accès du dashboard.

  1. La passerelle envoie un email avec un lien de confirmation, valable 24 heures et à usage unique. Le lien ouvre une page avec un bouton « Confirmer » : les filtres de messagerie (Safe Links…) ouvrent les liens qu'ils trouvent, la confirmation exige donc un clic.
  2. Domaine de confiance (trusted_domains) : l'accès est accordé tout de suite. L'utilisateur est créé avec le profil par défaut et sa clé gateway s'affiche une seule fois sur la page.
  3. Autre domaine : la demande attend une décision dans le dashboard ; les destinataires de notify (à défaut, ceux des alertes) sont prévenus. Approuver crée l'utilisateur avec le profil choisi et envoie un lien à usage unique vers la clé. Sans décision, la demande est refusée après 14 jours.

La clé n'est jamais envoyée par email. La page de demande répond toujours de la même façon, que l'adresse soit connue ou non. Les demandes sont limitées par adresse IP (5 par heure), par email (3 par jour) et au total (300 par jour) ; un lien inventé compte comme une connexion refusée pour la protection web. Chaque étape est inscrite au journal d'audit. Prérequis : le serveur SMTP de [alerts] et l'adresse publique [auth] base_url, vers laquelle pointent les liens.

6Filtrage et anonymisation

À l'aller, la passerelle détecte les données sensibles et applique l'action du profil. Au retour, elle remplace les jetons par les valeurs d'origine, y compris en streaming. L'utilisateur lit une réponse normale ; le fournisseur n'a vu que des jetons.

1 · Utilisateur
« Rédige un courrier pour Mme Claire Dubois, dossier DOS-2025-00042. »
2 · Passerelle
Détection : une personne, un numéro de dossier.
3 · LLM
Reçoit « … pour Mme «PERSON_1», dossier «DOSSIER_1». »
4 · Passerelle
Restaure les jetons dans la réponse, au fil du streaming.
5 · Utilisateur
« Madame Claire Dubois, concernant votre dossier DOS-2025-00042… »

Figure 2. Anonymisation bidirectionnelle. La correspondance jeton → valeur ne quitte pas la passerelle et n'est pas conservée.

Une mémoire des noms reconnaît ensuite un nom déjà repéré, même seul et même mal orthographié (« Keizr »). Elle ne contient que des empreintes chiffrées, jamais les noms.

Une liste « jamais anonymiser » protège les produits, les marques et les termes techniques (Claude, GitHub, API…) contre les faux positifs ; elle vaut pour le terme entier, si bien que « Mme Claude Dubois » reste pseudonymisé. Un dictionnaire de mots courants évite de prendre « Transport » ou « Custom » pour un nom de famille.

Ce qui est parcouru

  • Tout le texte de la requête : messages, système, documents texte, résultats d'outils et arguments de fonctions, noms des messages, descriptions et valeurs d'exemple des outils, champs user, metadata et stop, et le raisonnement des réponses précédentes que l'agent renvoie dans l'historique (reasoning, reasoning_content : DeepSeek, GLM, Grok, vLLM). Les signatures, les blocs chiffrés (encrypted_*) et les données base64 ne sont jamais modifiés.
  • Le texte JSON contenu dans une chaîne (résultat d'un outil, arguments d'une fonction) est analysé une fois ses échappements décodés ; le JSON envoyé reste valide.
  • Les espaces insécables, traits d'union conditionnels, caractères invisibles et chiffres pleine chasse sont neutralisés avant la détection : « 0470 12 34 56 » avec des espaces insécables est reconnu.
  • En cas de chevauchement, l'action la plus stricte l'emporte : un NISS interdit n'est jamais masqué par une référence seulement journalisée.
  • L'ordre de parcours est fixe (outils, système, messages) : la numérotation des jetons reste stable d'un tour à l'autre, et le cache de prompt des fournisseurs reste efficace.

Mémoire de conversation

Quand le client nomme sa conversation, la passerelle garde la correspondance des jetons pendant toute la conversation : « «PERSON_1» » reste la même personne d'un tour à l'autre, même si les noms apparaissent dans un autre ordre, et un nom repéré à un tour est encore reconnu aux tours suivants, même après une compaction de l'historique par l'agent.

  • Identifiant de conversation : en-tête X-LLMGW-Session (envoyé par le plugin Hermes), ou identifiant de session que Claude Code place dans metadata.user_id. Sans identifiant, chaque requête est numérotée seule, comme avant.
  • La correspondance reste en mémoire seulement, par utilisateur, profil et conversation ; elle est oubliée après 24 heures sans activité, ou au redémarrage de la passerelle. Au plus 5 000 conversations et 5 000 valeurs par conversation.
  • GET /v1/me, avec le même en-tête, donne le nombre de valeurs gardées par type, jamais les valeurs.

7Routage

La décision suit toujours le même chemin : clé → utilisateur → profil → LLM autorisés, dans l'ordre.

  • Modèles autorisés par cible, avec motifs (mistral-*, claude-*).
  • Repli automatique : si la première cible est en panne, saturée (429) ou en erreur (5xx), la suivante du profil prend le relais.
  • Cible imposée : mistral/mistral-large force une cible précise, si le profil l'autorise.
  • Alias : un nom demandé peut être traduit, par exemple claude-* vers deepseek-flash.
  • Formats : un client OpenAI est routé vers des cibles OpenAI, un client Anthropic vers des cibles Anthropic.
  • Cibles hors service : une cible sans clé ou un LLM local qui ne répond pas n'est pas proposé aux utilisateurs.

8Quotas et alertes

Quatre limites : requêtes par minute, requêtes par jour, tokens par jour, tokens par mois. Elles se fixent à trois niveaux :

  • par profil : la limite s'applique à chaque utilisateur du profil ;
  • par utilisateur : elle surcharge celle du profil, champ par champ ;
  • par LLM : un budget total partagé par tous. Une cible saturée est sautée au profit de la suivante.

Au dépassement, la requête est bloquée (erreur 429) ou simplement signalée, au choix.

Alertes par email : un récapitulatif toutes les N minutes, envoyé aux destinataires du profil et aux destinataires par défaut. Déclencheurs : violation, quota atteint, erreur d'un LLM, adresse bloquée par la protection web, et fichier bloqué dont la règle demande une alerte (envoyée même si le déclencheur « violation » est désactivé). Les messages ne contiennent aucune valeur sensible, seulement les types de données concernés.

10Mode DEBUG

Désactivé par défaut, activable le temps d'un diagnostic. Chaque échange est alors archivé : la requête telle que reçue par le LLM, la réponse brute, la correspondance jetons → valeurs et chaque mot détecté avec l'action appliquée.

  • Vue de l'échange : uniquement le nouveau message et la réponse, mots surlignés par action (bleu anonymisé, rouge bloqué, orange journalisé). Bascule entre vue anonymisée et vue d'origine.
  • Contexte complet, replié : prompt système et historique renvoyés par le client.
  • Vue globale : tout ce qui a été détecté dans l'archive, pour repérer les faux positifs récurrents.

Ce mode stocke des valeurs en clair. Purge automatique (24 heures par défaut), bandeau « DEBUG actif » dans le dashboard et bouton pour vider l'archive.

Journal des fichiers

« Journal » signifie qu'une trace est conservée 30 jours, même sans mode Debug : date, utilisateur, profil, LLM, type, nom du fichier, extension, taille, empreinte SHA-256 et action. Le contenu du fichier n'est jamais stocké. Les clients renvoient toute la conversation à chaque appel : un même fichier (même empreinte, même utilisateur, même action) n'est consigné qu'une fois par période de 12 heures.

Le nom d'un fichier peut lui-même être une donnée sensible (« Dossier_Dupont.pdf ») : l'accès au journal est réservé aux comptes Admin et Support.

13Langues de l'interface

Le dashboard et le chat s'affichent en anglais (par défaut), en français ou en néerlandais. Le choix se fait dans la liste en bas du menu du dashboard, dans l'en-tête du chat et sur les écrans de connexion ; il est mémorisé par navigateur. Les données (noms, descriptions, prompts, réponses des LLM) ne sont jamais traduites. Cette documentation est en français.

14Sécurité et confidentialité

  • Les clés des fournisseurs restent dans la passerelle ; les utilisateurs n'en ont jamais connaissance. Le dashboard ne les affiche pas.
  • Chaque utilisateur ou application a sa propre clé, révocable sans toucher aux autres.
  • SSO : code d'autorisation avec PKCE, state et nonce ; signature du jeton d'identité vérifiée avec les clés publiées par Microsoft ou Google ; session dans un cookie signé, HttpOnly, SameSite=Lax, Secure en HTTPS ; un en-tête obligatoire bloque les requêtes intersites.
  • Journaux et statistiques sans valeur sensible ; mémoire des noms sous forme d'empreintes chiffrées ; journal des fichiers sans contenu.
  • Rôles Admin et Support vérifiés côté serveur ; journal d'audit de 400 jours.
  • Configuration versionnée : les 10 dernières versions sont conservées, et un enregistrement est refusé si le fichier a changé entre-temps.
  • Déploiement : un seul binaire (macOS, Linux), base SQLite locale (droits 600), aucune dépendance externe.

Protection web (exposition sur Internet)

Section [security] et page Sécurité web du dashboard. Active par défaut ; les appels locaux (app Mac, tunnel SSH) et les réseaux exemptés ne sont jamais limités.

  • Limites par adresse : 600 requêtes par minute et 32 requêtes simultanées par défaut (IPv6 : par /64). Le travail d'anonymisation est en outre plafonné à deux fois le nombre de cœurs : au-delà, les requêtes attendent, puis reçoivent une erreur 503.
  • Blocage temporaire d'une adresse après 10 connexions refusées en 10 minutes : clé gateway ou jeton d'administration invalide, cookie falsifié, lien inventé. 30 minutes, doublées à chaque récidive (24 heures au plus). Chaque blocage est inscrit au journal d'audit et signalé par email (on_security).
  • Administration réservée aux adresses de admin_allow (dashboard et API d'administration).
  • Adresse réelle du client derrière un proxy de confiance (trusted_proxies, la machine locale par défaut) : elle sert aux limites, aux blocages et au journal d'audit. Un X-Forwarded-For envoyé directement par un client est ignoré.
  • En-têtes de sécurité sur toutes les réponses : Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, et HSTS en HTTPS.
  • HTTPS intégré (tls_cert, tls_key) pour une exposition sans proxy ; Caddy reste conseillé (certificats automatiques).
  • Secrets : une clé déjà enregistrée n'est conservée que pour l'adresse à laquelle elle était destinée. Changer l'adresse d'une cible demande de ressaisir sa clé, et une variable d'environnement qui alimente une cible ne peut pas être envoyée ailleurs depuis le dashboard. Les en-têtes HTTP des cibles ne sont plus renvoyés au navigateur.
  • Sessions web : rôle recalculé à chaque requête, déconnexion qui révoque la session, bouton « Fermer toutes les sessions » (nouvelle clé de signature). La redirection après connexion ne mène qu'au chat ou au dashboard.
  • Archive Debug purgée toutes les heures, même si personne ne la consulte ; les données effacées sont écrasées dans la base (secure_delete).
Setup

15Prérequis

  • Serveur : macOS ou Linux (x86-64 ou ARM). Ressources modestes : 1 à 2 vCPU et 1 à 2 Go de mémoire. La passerelle ajoute moins d'une milliseconde par Ko de texte nouveau (10 Ko : environ 4 ms ; 100 Ko : 15 ms en parallèle sur plusieurs cœurs) ; l'historique qu'un agent renvoie à chaque tour est mis en cache (100 Ko : 4 ms). Sur 2 cœurs, le débit dépasse 1 700 requêtes de 2 Ko par seconde : la latence des fournisseurs de LLM reste de loin le facteur dominant.
  • Réseau : accès sortant HTTPS du serveur vers les fournisseurs retenus ; accès entrant des postes vers la passerelle.
  • Clés des fournisseurs (Mistral, Anthropic, OpenAI, DeepSeek…), détenues par la passerelle uniquement.
  • Pour compiler : Go 1.25 ou plus récent. ./build.sh produit l'app Mac et les archives Linux dans dist/ (voir Installation).

16Installation

  1. Récupérer le code (dépôt privé VulpointLLMGw) : 
    git clone https://github.com/jsopdebeeck/VulpointLLMGw.git
cd VulpointLLMGw
  2. Compiler (./llmgw -version affiche la version) : 
    go build -o llmgw .                      # poste courant
./build.sh                               # tests, puis app Mac + DMG et archives Linux dans dist/
./build.sh --linux-only --skip-tests     # archives Linux seulement
    dist/ contient alors LLMGW.app et LLMGW-<version>.dmg (Mac, Apple Silicon et Intel), llmgw-<version>-linux-amd64.tar.gz et -arm64.tar.gz (binaire, setup.sh, service systemd, Caddyfile, LISEZMOI.txt) et SHA256SUMS.
  3. Préparer la configuration : 
    cp config.example.toml config.toml
./llmgw -config config.toml -check     # valide la configuration et quitte

Le binaire contient tout : le dashboard, le chat, cette documentation, la base SQLite et les dictionnaires. Aucune autre installation n'est nécessaire.

Hermes Agent : kit de raccordement

Le dossier integrations/hermes/ du dépôt raccorde Hermes en une commande, sur chaque poste (Hermes 0.21.6 ou plus récent) :

integrations/hermes/install.sh --url https://<passerelle> --key gw-hermes-…
integrations/hermes/install.sh --url https://<passerelle> --key gw-hermes-… --dry-run   # aperçu, rien n'est écrit
integrations/hermes/uninstall.sh                                                            # retour à la configuration d'origine
  • Configuration (via hermes config set, après une sauvegarde de config.yaml) : fournisseur llmgw avec les modèles autorisés par la passerelle, modèle principal, tâches auxiliaires (compression, vision, titres…), délégation, tâches planifiées et mélange de modèles (MoA) routés par la passerelle ; secours hors passerelle retirés. La clé va dans le .env de Hermes (droits 600), jamais dans config.yaml.
  • Plugin llmgw : refuse en mode strict un appel du modèle principal qui ne passe pas par la passerelle (--warn : signalement seulement) ; signale à la passerelle les tâches auxiliaires qui la contournent (journal d'audit, vue d'ensemble) ; commande /llmgw : passerelle, profil, quotas, consommation et valeurs pseudonymisées de la conversation.
  • Pseudonymes stables : Hermes envoie l'identifiant de la conversation (X-LLMGW-Session) à la passerelle seulement, tâches auxiliaires comprises ; la passerelle garde la même numérotation des jetons toute la conversation (voir Mémoire de conversation).
  • Hors passerelle, par décision : la recherche web, le navigateur, la voix et la génération d'images ou de vidéos ne sont pas des appels LLM au format OpenAI : le script les liste, avec la commande pour les couper, sans les modifier.

La passerelle doit nommer exactement au moins un modèle dans les cibles du profil de la clé (models = ["mistral-large-latest"]) : /v1/models ne liste pas les motifs ("mistral-*"). Le détail (modes, dépannage, limites) est dans integrations/hermes/README.md.

20Activer le SSO

HTTPS requis en production : Microsoft et Google refusent une adresse de retour en http://, sauf localhost pour les essais. Renseigner base_url avec l'adresse publique de la passerelle.

Microsoft Entra ID

  1. Portail Azure → Entra ID → Inscriptions d'applications → Nouvelle inscription, plateforme Web, adresse de retour https://<passerelle>/auth/callback/entra.
  2. Noter l'ID de tenant et l'ID client ; créer un secret client, à placer dans la variable ENTRA_CLIENT_SECRET du serveur.
  3. Profils par groupe : Configuration du jeton → ajouter la revendication de groupes, de préférence « groupes affectés à l'application » (le jeton est limité à 200 groupes).
  4. Administration : déclarer un rôle d'application LLMGW.Admin, puis l'affecter aux administrateurs dans Applications d'entreprise.

Google

  1. Google Cloud Console → API et services → Identifiants → ID client OAuth, type « Application Web », URI de redirection https://<passerelle>/auth/callback/google.
  2. Écran de consentement Interne pour un Google Workspace ; secret dans GOOGLE_CLIENT_SECRET.

21Réseau et HTTPS

  • La passerelle écoute sur l'adresse de [server] listen. Exposée sur Internet, elle se place derrière un reverse proxy HTTPS (Caddy, installé par setup.sh --domain), ou utilise le HTTPS intégré ([security] tls_cert et tls_key).
  • Derrière un proxy, déclarer son adresse dans [security] trusted_proxies (la machine locale par défaut) : la passerelle lit alors l'adresse du client dans X-Forwarded-For, pour les limites, les blocages et le journal d'audit.
  • Renseigner [auth] base_url avec l'adresse publique : retours SSO et liens des demandes d'accès.
  • Firewall et Umbrella : autoriser uniquement le serveur de la passerelle vers les domaines des fournisseurs de LLM ; bloquer ces domaines pour tous les postes.
  • Postes et agents : autoriser l'adresse de la passerelle.

Avec Caddy (deploy/Caddyfile), le streaming exige flush_interval -1 et aucune compression ; le dashboard peut être limité à des adresses par un remote_ip. Exemple nginx, où le streaming exige de désactiver la mise en mémoire tampon :

location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_buffering off;            # réponses en streaming
    proxy_read_timeout 600s;        # longues générations
    client_max_body_size 50m;       # documents joints
    proxy_set_header X-Forwarded-For $remote_addr;   # adresse du client (remplace la valeur reçue)
    proxy_set_header X-Forwarded-Proto $scheme;
}
