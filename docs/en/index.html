LLMGW, the organisation's AI gateway

A single connection point between users, agents and language models. It enforces the AI policy: who may use which model, which data may leave, and with what traceability.

Version 1.5.5 (25 October 2026)Component llmgw (single Go binary, macOS and Linux)API formats OpenAI and AnthropicInterface English, French, Dutch

Features

1Purpose

Strengthen the AI policy by enforcing a single path to the LLMs. Direct access to the providers (OpenAI, Anthropic, Mistral, DeepSeek…) is blocked in the firewalls and in Cisco Umbrella. Only the gateway is allowed to reach them.

This central point makes it possible to:

  • control access: each user or application identifies itself with its own key and is given a profile;
  • protect data: sensitive information is replaced by tokens before it leaves the organisation, then restored in the answer;
  • choose the model according to the profile, with automatic fallback when a provider is down;
  • measure volumes, response times, conversions and violations.

2Architecture

On the left, the trust zone: users, agents, applications and local LLMs. On the right, the Internet, an uncontrolled zone: the cloud LLMs. The gateway sits on the boundary: every request to an LLM goes through it, and it is the only component allowed to reach the providers.

Figure 1. Trust zone on the left, Internet on the right, gateway on the boundary. Allowed flows as solid lines; direct access to the Internet blocked (red dashes).

3Access

Web portal /chat

For users. Sign in with Microsoft (Entra ID), Google or a personal key, then pick a model among those the profile allows. Someone without access can request it (see Access requests).

  • Attached documents: txt, md, csv, json, PDF, docx. The text is extracted in the browser, then anonymised by the gateway.
  • Images and files handled according to the profile: sent, replaced by a white square, or refused (see 11. Images and files).
  • History of the last 10 conversations, kept in the browser; Help button leading to the user guide.
  • Under each answer: the model used and the number of pseudonymised values.

API agents and applications

For agents (Claude Cowork, Claude Code, Hermes) and applications. Same address as the portal, with an application key.

  • OpenAI format: /v1/chat/completions, /v1/models.
  • Anthropic format: /v1/messages, /v1/messages/count_tokens.
  • /v1/me: the caller's profile, quotas and consumption.
  • Streaming supported in both formats.

4Authentication

Every access is identified. Three methods coexist; SSO is added to the keys without replacing them.

MethodFor whomWhere
OpenID Connect SSOpeople: Microsoft Entra ID, Google, or any OIDC provider (Okta, Keycloak…)web portal and dashboard
Gateway keypeople without SSO, agents and applicationsweb portal (can be disabled) and API
Admin tokentechnical administrator, emergency accessdashboard

Profile assigned after an SSO sign-in

  1. A declared user with the same email address keeps their profile and quotas.
  2. Otherwise, the first matching rule: Entra group → profile, app role → profile, or email pattern (*@example.com) → profile.
  3. Otherwise, the provider's default profile.
  4. Otherwise, access is refused with an explicit message.

Administrators are designated by app role, Entra group or email address, or listed in the administration accounts (Admin or Support): they open the dashboard without a token. Google does not send groups: with Google, profiles are assigned by domain, by email or by declared user.

Joiners, leavers and department changes follow the directory. Role and profile are recomputed at every request with the configuration in force: removing a rule, an account or a user takes effect immediately. A group change in the directory takes effect at the next sign-in (12-hour session by default). Signing out revokes the session, even if its cookie was copied.

Identity used: for Entra ID, the UPN, set by the tenant administrators; for Google and other OIDC providers, the email address marked as verified by the provider, otherwise the sign-in is refused. An OIDC provider that does not send this flag is accepted with trust_unverified_email = true, only if nobody can register on it freely.

Access requests

Someone without access can request it from the chat sign-in screen (« Request access » link: name, email, reason). Section [access], Access requests tab of the dashboard.

  1. The gateway sends an email with a confirmation link, valid for 24 hours and single-use. The link opens a page with a « Confirm » button: mail filters (Safe Links…) open the links they find, so confirmation requires a click.
  2. Trusted domain (trusted_domains): access is granted at once. The user is created with the default profile and their gateway key is shown only once on the page.
  3. Other domain: the request waits for a decision in the dashboard; the notify recipients (failing that, the alert recipients) are informed. Approving creates the user with the chosen profile and sends a single-use link to the key. Without a decision, the request is refused after 14 days.

The key is never sent by email. The request page always answers the same way, whether the address is known or not. Requests are limited per IP address (5 per hour), per email (3 per day) and in total (300 per day); an invented link counts as a refused sign-in for web protection. Each step is written to the audit log. Requirements: the SMTP server of [alerts] and the public address [auth] base_url, which the links point to.

A profile groups everything that applies to a user or an application: allowed models, data policy, images and files by extension, a behaviour prompt, quotas and alert recipients. Each key is attached to a single profile.

6Filtering and anonymisation

On the way out, the gateway detects sensitive data and applies the profile's action. On the way back, it replaces the tokens with the original values, streaming included. The user reads a normal answer; the provider only saw tokens.

1 · User
« Write a letter for Mrs Claire Dubois, case DOS-2025-00042. »
2 · Gateway
Detection: one person, one case number.
3 · LLM
Receives « … for Mrs «PERSON_1», case «DOSSIER_1». »
4 · Gateway
Restores the tokens in the answer, as it streams.
5 · User
« Dear Mrs Claire Dubois, regarding your case DOS-2025-00042… »

Figure 2. Bidirectional anonymisation. The token → value mapping never leaves the gateway and is not kept.

A name memory then recognises a name already found, even on its own and even misspelt (« Keizr »). It only holds encrypted fingerprints, never the names.

A « Never anonymise » list protects products, brands and technical terms (Claude, GitHub, API…) against false positives; it applies to the whole term, so « Mrs Claude Dubois » is still pseudonymised. A dictionary of common words prevents « Transport » or « Custom » from being taken for a surname.

What is scanned

  • All the text of the request: messages, system, text documents, tool results and function arguments, message names, tool descriptions and example values, the user, metadata and stop fields, and the reasoning of previous answers that the agent sends back in the history (reasoning, reasoning_content: DeepSeek, GLM, Grok, vLLM). Signatures, encrypted blocks (encrypted_*) and base64 data are never changed.
  • JSON text held in a string (a tool result, function arguments) is analysed once its escapes are decoded; the JSON sent stays valid.
  • Non-breaking spaces, soft hyphens, invisible characters and full-width digits are neutralised before detection: « 0470 12 34 56 » with non-breaking spaces is recognised.
  • When matches overlap, the strictest action wins: a forbidden NISS is never hidden by a reference that is only logged.
  • The scanning order is fixed (tools, system, messages): token numbering stays stable from one turn to the next, and the providers' prompt cache stays effective.

Conversation memory

When the client names its conversation, the gateway keeps the token mapping for the whole conversation: « «PERSON_1» » stays the same person from one turn to the next, even if the names appear in a different order, and a name found in one turn is still recognised in the following turns, even after the agent compacts the history.

  • Conversation identifier: the X-LLMGW-Session header (sent by the Hermes plugin), or the session identifier that Claude Code puts in metadata.user_id. Without an identifier, each request is numbered on its own, as before.
  • The mapping is kept in memory only, per user, profile and conversation; it is forgotten after 24 hours without activity, or when the gateway restarts. At most 5,000 conversations and 5,000 values per conversation.
  • GET /v1/me, with the same header, gives the number of values kept per type, never the values.

7Routing

The decision always follows the same path: key → user → profile → allowed LLMs, in order.

  • Allowed models per target, with patterns (mistral-*, claude-*).
  • Automatic fallback: if the first target is down, saturated (429) or failing (5xx), the next one in the profile takes over.
  • Forced target: mistral/mistral-large forces a specific target, if the profile allows it.
  • Aliases: a requested name can be translated, for example claude-* to deepseek-flash.
  • Formats: an OpenAI client is routed to OpenAI targets, an Anthropic client to Anthropic targets.
  • Unavailable targets: a target without a key, or a local LLM that does not answer, is not offered to users.

8Quotas and alerts

Four limits: requests per minute, requests per day, tokens per day, tokens per month. They are set at three levels:

  • per profile: the limit applies to each user of the profile;
  • per user: it overrides the profile's limit, field by field;
  • per LLM: a total budget shared by everyone. A saturated target is skipped in favour of the next one.

When a limit is exceeded, the request is blocked (error 429) or simply reported, as you choose.

Email alerts: a summary every N minutes, sent to the profile's recipients and to the default recipients. Triggers: violation, quota reached, LLM error, address banned by web protection, and blocked file whose rule asks for an alert (sent even if the « violation » trigger is disabled). The messages contain no sensitive value, only the data types concerned.

10DEBUG mode

Off by default, can be switched on for the duration of a diagnosis. Each exchange is then archived: the request as received by the LLM, the raw response, the token → value mapping and every detected word with the action applied.

  • Exchange view: only the new message and the answer, with words highlighted by action (blue anonymised, red blocked, orange logged). Toggle between the anonymised view and the original view.
  • Full context, collapsed: system prompt and history sent back by the client.
  • Global view: everything detected in the archive, to spot recurring false positives.

This mode stores values in clear text. Automatic purge (24 hours by default), « DEBUG on » banner in the dashboard and a button to empty the archive.

File log

« Log » means that a record is kept for 30 days, even without Debug mode: date, user, profile, LLM, type, file name, extension, size, SHA-256 fingerprint and action. The file content is never stored. Clients send the whole conversation at each call: the same file (same fingerprint, same user, same action) is recorded only once per 12-hour period.

A file name can itself be sensitive data (« Dossier_Dupont.pdf »): access to the log is restricted to Admin and Support accounts.

13Interface languages

The dashboard and the chat are shown in English (default), French or Dutch. The choice is made in the list at the bottom of the dashboard menu, in the chat header and on the sign-in screens; it is remembered per browser. Data (names, descriptions, prompts, LLM answers) is never translated. This documentation is available in English (this page) and in French.

14Security and confidentiality

  • Provider keys stay in the gateway; users never know them. The dashboard does not display them.
  • Each user or application has its own key, revocable without affecting the others.
  • SSO: authorisation code with PKCE, state and nonce; ID token signature checked against the keys published by Microsoft or Google; session in a signed cookie, HttpOnly, SameSite=Lax, Secure over HTTPS; a mandatory header blocks cross-site requests.
  • Logs and statistics without sensitive values; name memory stored as encrypted fingerprints; file log without content.
  • Admin and Support roles checked on the server side; 400-day audit log.
  • Versioned configuration: the last 10 versions are kept, and a save is refused if the file has changed in the meantime.
  • Deployment: a single binary (macOS, Linux), local SQLite database (permissions 600), no external dependency.

Web protection (exposure on the Internet)

Section [security] and Web security page of the dashboard. On by default; local calls (Mac app, SSH tunnel) and exempt networks are never limited.

  • Per-address limits: 600 requests per minute and 32 concurrent requests by default (IPv6: per /64). Anonymisation work is also capped at twice the number of cores: beyond that, requests wait, then receive a 503 error.
  • Temporary ban of an address after 10 refused sign-ins in 10 minutes: invalid gateway key or admin token, forged cookie, invented link. 30 minutes, doubled at each repeat (24 hours at most). Each ban is written to the audit log and reported by email (on_security).
  • Administration restricted to the addresses in admin_allow (dashboard and administration API).
  • Real client address behind a trusted proxy (trusted_proxies, the local machine by default): it is used for limits, bans and the audit log. An X-Forwarded-For sent directly by a client is ignored.
  • Security headers on all responses: Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, and HSTS over HTTPS.
  • Built-in HTTPS (tls_cert, tls_key) for exposure without a proxy; Caddy is still recommended (automatic certificates).
  • Secrets: a key already stored is kept only for the address it was intended for. Changing a target's address requires re-entering its key, and an environment variable that feeds a target cannot be sent elsewhere from the dashboard. Targets' HTTP headers are no longer sent back to the browser.
  • Web sessions: role recomputed at every request, sign-out that revokes the session, « Close all sessions » button (new signing key). The redirect after sign-in only leads to the chat or the dashboard.
  • Debug archive purged every hour, even if nobody views it; erased data is overwritten in the database (secure_delete).
Setup

15Requirements

  • Server: macOS or Linux (x86-64 or ARM). Modest resources: 1 to 2 vCPU and 1 to 2 GB of memory. The gateway adds less than one millisecond per KB of new text (10 KB: about 4 ms; 100 KB: 15 ms in parallel on several cores); the history an agent sends back at each turn is cached (100 KB: 4 ms). On 2 cores, throughput exceeds 1,700 requests of 2 KB per second: the latency of the LLM providers remains by far the dominant factor.
  • Network: outbound HTTPS access from the server to the chosen providers; inbound access from workstations to the gateway.
  • Provider keys (Mistral, Anthropic, OpenAI, DeepSeek…), held by the gateway only.
  • To build: Go 1.25 or later. ./build.sh produces the Mac app and the Linux archives in dist/ (see Installation).

16Installation

  1. Get the code (private repository VulpointLLMGw): 
    git clone https://github.com/jsopdebeeck/VulpointLLMGw.git
cd VulpointLLMGw
  2. Build (./llmgw -version shows the version): 
    go build -o llmgw .                      # current machine
./build.sh                               # tests, then Mac app + DMG and Linux archives in dist/
./build.sh --linux-only --skip-tests     # Linux archives only
    dist/ then contains LLMGW.app and LLMGW-<version>.dmg (Mac, Apple Silicon and Intel), llmgw-<version>-linux-amd64.tar.gz and -arm64.tar.gz (binary, setup.sh, systemd service, Caddyfile, LISEZMOI.txt) and SHA256SUMS.
  3. Prepare the configuration: 
    cp config.example.toml config.toml
./llmgw -config config.toml -check     # validates the configuration and exits

The binary contains everything: the dashboard, the chat, this documentation, the SQLite database and the dictionaries. No other installation is needed.

Fresh Linux server (Ubuntu 22.04 / 24.04, Debian 12)

setup.sh, shipped in the Linux archive, installs or updates the gateway on a freshly installed server. It is safe to run again: an update keeps the configuration, the database and the Caddyfile.

scp dist/llmgw-<version>-linux-amd64.tar.gz admin@server:
ssh admin@server
tar xzf llmgw-<version>-linux-amd64.tar.gz && cd llmgw-<version>
sudo ./setup.sh --domain gateway.example.com --email it@example.com --admin-ip 203.0.113.7
  • Packages and automatic security updates (unattended-upgrades), fail2ban for SSH, ufw firewall (SSH first, then 80 and 443).
  • System user llmgw, folder /opt/llmgw (700), hardened systemd service, secrets.env (600) for the provider keys.
  • First installation: config.toml generated with an admin token and random example keys, listening on the local machine, trusted proxies and administration addresses. The token is shown once and kept in /opt/llmgw/admin_token.txt (root, 600).
  • With --domain: Caddy and its Let's Encrypt certificate; the dashboard can only be reached from the --admin-ip addresses (otherwise through an SSH tunnel).
  • The new binary validates the configuration before replacing the old one; if it does not start, the previous version is restored.
  • Daily backup of the database and the configuration in /var/backups/llmgw, kept for 14 days.

From the Mac, deploy/deploy.sh does everything in one command: build, copy of the archive, run of setup.sh.

deploy/deploy.sh --domain gateway.example.com --email it@example.com --admin-ip 203.0.113.7 admin@server
deploy/deploy.sh admin@server            # update

setup.sh does not change SSH: disable password sign-in yourself (PasswordAuthentication no) once your SSH key is in place.

17Configuration

The whole configuration lives in config.toml. The file is reloaded automatically at each change; an invalid configuration is refused and the previous one stays active. Most settings are then made from the dashboard.

SectionContent

[targets.<name>]an LLM: API format, address, key (preferably through the environment variable api_key_env; if it is not set, api_key is used as the key), models, aliases, quota
[profiles.<name>]allowed LLMs in order, default action, actions per type, images (pass, blank, block), files per extension (pass_log, blank, block, block_alert) and files_default, behaviour prompt, alerts, quota
[users.<name>]person or application: gateway key, profile, individual quota, email (link with the SSO identity)
[auth]SSO: public address, session duration, Entra ID / Google / OIDC providers, group and role → profile rules, administrators
[[admins]]administration accounts: email, name, role (admin or support), Debug access, deactivation
[[detectors]]detectors: built-in (email, NISS, IBAN, names, addresses…), patterns, term lists
[privacy]terms never anonymised

[security]web protection: trusted proxies, administration addresses, exempt networks, per-address limits, bans, built-in HTTPS

Minimal example of a target and a user:

[targets.mistral]
api = "openai"
base_url = "https://api.mistral.ai/v1"
api_key_env = "MISTRAL_API_KEY"
models = ["mistral-*"]

[users.alice]
key = "gw-alice-…"          # key generated from the dashboard

[profiles.anonymisation]
images = "blank"                                   # white square

Before going live: set a long, random admin_token (for example openssl rand -hex 24). Without it, the dashboard is open to anyone who can reach the gateway.

18Startup and service

Manual start

export MISTRAL_API_KEY=… ANTHROPIC_API_KEY=…
./llmgw -config config.toml
# LLMGW 1.5.5 listening on http://127.0.0.1:8088 (dashboard: /dashboard, documentation: /docs)

One instance per port. Stop with Ctrl+C: pending metrics are saved before exiting.

macOS menu bar app

macapp/build.sh builds a self-contained LLMGW.app in dist/, and dist/LLMGW-<version>.dmg to install it by drag and drop into Applications; macapp/build.sh --install installs it directly in Applications (and restarts the app if it was running). Go and the Xcode Command Line Tools are only needed for the build: the app embeds the gateway (universal binary for Apple Silicon and Intel, no dependency outside macOS) and needs nothing else to run.

The data lives in ~/Library/Application Support/LLMGW: config.toml, secrets.env, the database and the log. At first launch, the app creates a starter configuration there, with a random admin token, and a secrets.env template (permissions 600). An existing installation (a folder that already contains config.toml) is taken over as is through « Data folder… ».

Double-clicking the app shows an icon in the menu bar:

  • a status dot: green when running, orange while starting, red when stopped, grey if the gateway folder cannot be found;
  • Start, Stop, Restart; a gateway started elsewhere is recognised and can be stopped;
  • Open the dashboard, Open the chat, Documentation;
  • Copy the admin token, to sign in to the dashboard;
  • Edit the configuration and Edit the secrets (API keys, SSO secrets) in TextEdit; the configuration can also be edited from the dashboard;
  • Show the log (llmgw.log, in Console), the data folder, and Data folder… to choose another one;
  • Open at login, for a gateway available as soon as you sign in to the Mac;
  • menu in English, French or Dutch.

The app loads secrets.env, starts the gateway when it opens and stops it when you quit. Without the app, start.command starts the gateway in Terminal with a double-click and opens the dashboard.

setup.sh installs this service (deploy/llmgw.service, with additional systemd hardening). For a manual installation:

Hermes Agent: connection kit

The repository's integrations/hermes/ folder connects Hermes in one command, on each workstation (Hermes 0.21.6 or later):

integrations/hermes/install.sh --url https://<gateway> --key gw-hermes-…
integrations/hermes/install.sh --url https://<gateway> --key gw-hermes-… --dry-run   # preview, nothing is written
integrations/hermes/uninstall.sh                                                            # back to the original configuration
  • Configuration (through hermes config set, after a backup of config.yaml): llmgw provider with the models the gateway allows, main model, auxiliary tasks (compression, vision, titles…), delegation, scheduled tasks and mixture of agents (MoA) routed through the gateway; fallbacks outside the gateway removed. The key goes into Hermes's .env (permissions 600), never into config.yaml.
  • llmgw plugin: in strict mode, refuses a main-model call that does not go through the gateway (--warn: report only); reports to the gateway the auxiliary tasks that bypass it (audit log, overview); /llmgw command: gateway, profile, quotas, consumption and pseudonymised values of the conversation.
  • Stable pseudonyms: Hermes sends the conversation identifier (X-LLMGW-Session) to the gateway only, auxiliary tasks included; the gateway keeps the same token numbering for the whole conversation (see Conversation memory).
  • Outside the gateway, by decision: web search, the browser, voice and image or video generation are not OpenAI-format LLM calls: the script lists them, with the command to turn them off, without changing them.

The key's profile must allow at least one model. /v1/models lists the named models ("mistral-large-latest") and, for a target described by a pattern ("grok-*"), the provider's models that match it (list requested from the provider and kept for 10 minutes). A narrower pattern ("grok-4*") excludes image and video models. Details (modes, troubleshooting, limitations) are in integrations/hermes/README.md.

20Enabling SSO

HTTPS required in production: Microsoft and Google refuse an http:// redirect address, except localhost for testing. Set base_url to the gateway's public address.

Microsoft Entra ID

  1. Azure portal → Entra ID → App registrations → New registration, Web platform, redirect URI https://<gateway>/auth/callback/entra.
  2. Note the Tenant ID and the Client ID; create a client secret, to be placed in the server's ENTRA_CLIENT_SECRET variable.
  3. Profiles by group: Token configuration → add the groups claim, preferably « groups assigned to the application » (the token is limited to 200 groups).
  4. Administration: declare an app role LLMGW.Admin, then assign it to administrators in Enterprise applications.

Google

  1. Google Cloud Console → APIs & Services → Credentials → OAuth client ID, type « Web application », redirect URI https://<gateway>/auth/callback/google.
  2. Internal consent screen for a Google Workspace; secret in GOOGLE_CLIENT_SECRET.

At startup, the log shows each provider's redirect address; the Alerts and SSO page of the dashboard shows it too. To make the portal SSO-only: disable_keys = true (keys remain valid for the API).

21Network and HTTPS

  • The gateway listens on the [server] listen address. When exposed on the Internet, it sits behind an HTTPS reverse proxy (Caddy, installed by setup.sh --domain), or uses the built-in HTTPS ([security] tls_cert and tls_key).
  • Behind a proxy, declare its address in [security] trusted_proxies (the local machine by default): the gateway then reads the client address from X-Forwarded-For, for limits, bans and the audit log.
  • Set [auth] base_url to the public address: SSO redirects and access request links.
  • Firewall and Umbrella: allow only the gateway server to reach the LLM providers' domains; block those domains for all workstations.
  • Workstations and agents: allow the gateway's address.

With Caddy (deploy/Caddyfile), streaming requires flush_interval -1 and no compression; the dashboard can be restricted to certain addresses with a remote_ip. nginx example, where streaming requires buffering to be disabled:

location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_buffering off;            # streaming responses
    proxy_read_timeout 600s;        # long generations
    client_max_body_size 50m;       # attached documents
    proxy_set_header X-Forwarded-For $remote_addr;   # client address (replaces the received value)
    proxy_set_header X-Forwarded-Proto $scheme;
}
Dashboard pages

Screenshots taken on a demonstration instance, with the interface in French (the English interface has the same layout): users, figures and sensitive data are fictitious. The bottom of the menu holds the theme, the language, the Documentation button (this page) and the version.

22Sign-in

Address /dashboard. SSO sign-in restricted to administration accounts (Admin or Support) and to the providers' rules, or admin token. A signed-in person without rights is told so. The language can be chosen from this screen.

23Overview

  • Indicators for the last 48 hours: requests and errors, tokens, average LLM response time, conversions, violations, active users.
  • Points of attention sorted by severity, each with a button to the page concerned: DEBUG mode, blocked requests, errors, alerts, targets without a key, administration protection, quotas close to the limit.
  • Recent activity and Most active users.

24Reporting

  • Period: 48 h, 60 d, 6 weeks, 6 months (maximum depth).
  • Indicators: requests, tokens, volume, total time, LLM and gateway time (median, p95), conversions, violations.
  • Charts: requests per LLM, tokens per user, IN / Gateway / LLM response times, conversions and violations.
  • Tables per user, per LLM and per application (Hermes, Claude Code, chat…, recognised by the X-LLMGW-Client header or the User-Agent, over the detail period), detections per type, recent requests with the application and the reason for errors.

25Users

One row per person or application: type, description, profile, accessible LLMs, key preview and generation of a new key (shown in full until the page is reloaded), blocking, today's consumption. People who sign in with SSO do not need to be listed: their profile comes from the directory. Every change goes through the « Save » bar at the bottom of the screen.

26Access requests

Requests made from the portal (see Access requests). Filters: Pending, Not confirmed, Handled, All. For each request: date, name and email, domain (trusted or external), reason, status, and who handled it. A pending request is approved with the chosen profile or refused; an approved request can be sent a new link to its key. The counter in the menu gives the number of pending requests, also shown in the overview. At the bottom, the settings (Admin): activation, trusted domains, default profile, people notified, link validity, automatic refusal. Available to the Admin and Support roles.

27Profiles

One collapsible card per profile; clicking the title opens it. The title is green if the profile is in use (user or SSO rule), grey otherwise. An open card shows the allowed LLMs in fallback order, the behaviour prompt, the alert emails, the image policy, a summary of the file, data and quota rules, and the list of users.

28Target LLMs

  • One collapsible card per LLM, with a status light: green connected (with the response time), red unreachable or key refused, grey disabled or not tested. « Retest all » runs the tests again.
  • Open card: API format, address, allowed models, aliases, key (environment variable or masked value), HTTP headers, options, profiles that use it.
  • Test queries the LLM with the saved key and lists its models.

29Quotas

  • Three tables: per profile, per user (override, −1 = unlimited) and per LLM (shared budget).
  • Action when exceeded: block or alert.
  • Live gauges: current minute, today's requests and tokens, this month's tokens; orange at 80%, red at 100%.

30Filtering and privacy

Five tabs:

  • Detectors: token type, method (built-in, regular expression, term list), parameter, priority order.
  • Rules per profile: a data type × profile table, with the action in each cell, the image policy and the « tokens » instruction given to the LLMs. In bold, what differs from the default action; in red, blocks.
  • Files: an extension × profile table. Two header rows set images without an extension rule and other files; each extension can then get its own action. In brackets and grey, the action inherited from the default. « + Extension » adds an extension missing from the list.
  • Exceptions and memory: « Never anonymise » list and name memory (number of entries, « Forget all » button).
  • Test: a text, a profile, and the result with the tokens and the mapping table. Nothing is sent to an LLM.

31File log

Files and images sent with log, blocked, or blocked with alert, over 30 days: date, user, profile, LLM, type, file name, size, action and beginning of the SHA-256 fingerprint (full fingerprint on hover). A filter searches all columns. Available to the Admin and Support roles.

32Debug

  • DEBUG mode: activation, retention period, number of archived exchanges, Empty button.
  • Archived exchanges: one row per request with the detections coloured by action.
  • Exchange detail: what was detected in the new message and in the answer, the message as received by the LLM, the raw response, then the full context, collapsed. Toggle between anonymised view and original view.
  • Global view: all values detected in the archive, with a filter.

33Alerts and SSO

  • Email alerts: activation, triggers (violation, quota, LLM error), default recipients, summary frequency, SMTP server, sending a test. « Blocked + alert + log » files are reported in addition.
  • Authentication (SSO): configured providers, redirect address to declare, domains, assigned profile, administrators.

34Web security

  • Web protection: your address as the gateway sees it (direct or behind a trusted proxy), per-address limits, ban after refused sign-ins, addresses allowed for administration, trusted proxies, exempt networks, built-in HTTPS. Check that your address is in « Administration from » before saving.
  • Banned addresses: address, end of the ban, number of bans, reason; button to unban.
  • Web sessions: « Close all sessions » signs everyone out (new session signing key).

35Administration accounts

The list of people allowed in the dashboard: email, name, role (Admin or Support), Debug access for a Support account, deactivation (cuts access immediately), last sign-in. A table recalls the rights per role, then the other ways in: SSO provider rules and admin token.

36Audit log

Who did what, and when: date, actor, role, action, target and detail of the changes. A filter searches all fields. No sensitive value appears in it.
